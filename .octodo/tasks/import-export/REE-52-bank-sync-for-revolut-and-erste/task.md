Research findings as of 2026-11-02, against Actual master at `741d1615`. Nothing here has been run against a real bank, and no decision has been made to build it: [scope rules](../../../../docs/rules/scope.md) still leaves bank sync out. The research notes behind this are attached to this task.

**Open question:** the first two letters of the Erste IBAN, plus the country of residence if they are CZ.

Related: REE-23 (re-importing deleted transactions) becomes a requirement if this is built.

Yes, reeve can sync Revolut and Erste, but not with a simple API key from either bank, and not fully hands-free. For almost everyone, the route is a licensed middleman called an aggregator, and the only one a private person can verifiably join today for free is **Enable Banking's restricted mode** ([Terms](https://enablebanking.com/terms)). You hold your own private key on your machine and approve access at each bank in a browser. You then repeat that approval roughly every 90 to 180 days, and reeve fetches read-only data in between. The main exception is the Czech Republic: Enable Banking excludes Czech residents, while Česká spořitelna documents a licence-free personal API that no one has been shown to get production keys for. **My recommendation is to build nothing yet.** Spend an afternoon on the tests at the end of this report. If they pass, build one Enable Banking adapter that imports booked transactions only, keep file import as a first-class fallback, and supersede [scope rules](../../../../docs/rules/scope.md) before writing code. The largest piece of work is not the bank connection but making reeve's ledger safe for repeated imports. No part of this has been run against a real bank: everything below comes from documents, code and user reports.

## Banks admit licensed firms, so you borrow one

An EU law called PSD2 forces banks to let customers share account data with outside apps, through a dedicated interface. A firm that reads accounts this way is an **account information service provider (AISP)**, and it is one kind of **third-party provider (TPP)**. Before a TPP can read anything, the customer must approve it at the bank with **strong customer authentication (SCA)**, meaning a real login confirmed by something like a phone app. That approval is called **consent**, and it expires.

The barrier for a private person is more technical than legal. Banks identify TPPs by qualified certificates, called **QWAC** and **QSealC**, and the law says the registration number inside them is the provider's regulator-issued **authorisation number** ([RTS Art. 34, mirror](https://lawplayer.com/eu/act/32018R0389)). With no licence there is no number, so you can't get the certificate. The certificates themselves are not the expensive part: public list prices run from about EUR 135 to 450 a year ([Disig](https://eidas.disig.sk/en/qualified-certificates/pricelist), [HARICA](https://news.harica.gr/tags/qwac/)), far below the thousands claimed in forum posts.

A natural person can legally register as an AISP ([PSD2 Art. 33, mirror](https://lawplayer.com/eu/act/32015L2366)), but a vendor estimates the required insurance alone at EUR 5,000 to 30,000 a year ([Crassula](https://crassula.io/guides/licenses/aisp/)). I found no exemption for reading "your own data", and no regulator ruling either way. This is not legal advice.

An **aggregator** holds the licence and certificates and offers developers one API across many banks. Enable Banking is a registered AISP supervised by the Finnish regulator ([Enable Banking](https://enablebanking.com/docs/markets/at/)). Waiting for new law won't help: PSD3 and the PSR apply in practice from about the end of 2028 ([Dudkowiak & Putyra](https://www.dudkowiak.com/blog/psd3-and-psr-eu-council-publishes-final-texts-when-will-the-new-rules-apply/)), and FIDA has no agreed text ([FinanceX](https://financexmagazine.com/post/open-banking-picks-a-lane-psd3-edges-forward-fida-wobbles-core-banking-finally-ships)).

## Enable Banking is the one open door for a new user

Enable Banking's terms limit restricted production use to linked accounts, "solely for evaluation purposes or for the personal use of private individuals" ([Terms, 9 Jan 2026](https://enablebanking.com/terms)). I saw no fee for it in the terms, and third parties describe it as free ([Firefly III](https://docs.firefly-iii.org/tutorials/data-importer/eb/)). You register an application, choose "Activate by linking accounts", and authorise at the bank ([linked accounts docs](https://enablebanking.com/docs/api/linked-accounts/)). Requests are signed with your own RSA key as an RS256 JWT ([API reference](https://enablebanking.com/docs/api/reference/)). That key is the "API key or similar" you asked about, but it identifies your application. It does not replace the bank approval.

The alternatives are closed, off-region or commercial:

| Provider                     | Position for a new private user in the EU                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GoCardless Bank Account Data | "New signups... are currently disabled" ([GoCardless](https://bankaccountdata.gocardless.com/new-signups-disabled))                                                                   |
| SimpleFIN                    | US and Canada versions of banks only ([SimpleFIN](https://beta-bridge.simplefin.org/search-institutions))                                                                             |
| Tink, Yapily                 | Sales-led ([Tink](https://tink.com/pricing/), [Yapily](https://www.yapily.com/pricing))                                                                                               |
| YAXI                         | Self-serve free tier to 1,000 calls a month, but Revolut and Erste coverage and its rules for individuals are unconfirmed ([YAXI](https://yaxi.tech/)). Worth keeping as a lead       |
| Lunch Flow                   | A hosted consumer middleman, at GBP 5 a month on a January 2025 price ([changelog](https://lunchflow.featurebase.app/en/changelog/self-service-tiered-pricing)). Coverage unconfirmed |

Three terms affect how reeve ships. Each user must register their own application, because the terms exclude accounts "that does not belong to the Control Panel user", so reeve can't ship a shared key. Business use is excluded, and breach of the use restriction carries full liability ([Terms](https://enablebanking.com/terms)). Whether a joint household account counts as yours is unclear, so read that clause if it applies. One report says the registration form also asks for a description, a data-protection email, and privacy and terms URLs ([picsou-finance #318](https://github.com/Cloeille/picsou-finance/issues/318)).

Bank data also passes through this third party, so "local-only" means your budget stays on your machine, not that no one else ever handles your bank data. The API says it "does not store the account information it processes" ([FAQ](https://enablebanking.com/docs/faq/)). Its privacy notice separately says personal data "is retained indefinitely", in a section about Control Panel use ([Privacy Notice](https://enablebanking.com/privacy/)).

User reports show what to expect from Revolut data through Enable Banking. `entry_reference` was present on 53 of 53 sampled postings, a good sign for de-duplication ([#7799](https://github.com/actualbudget/actual/issues/7799#issuecomment-5386573157)). The payee sits in the second remittance row, so a small per-bank mapping is needed ([#7799](https://github.com/actualbudget/actual/issues/7799#issuecomment-4826326037)). The reported balance can include pending card authorisations ([Sure #314](https://github.com/newmancu/sure/issues/314)), so it is unsafe as a reconciliation anchor. Pockets may be hard to tell apart ([Firefly #13056](https://github.com/firefly-iii/firefly-iii/issues/13056)). reeve has no per-account currency column, so each Revolut currency needs its own reeve account.

One community write-up calls Enable Banking "contract-gated" ([k8s-titan #159](https://github.com/javierarrieta/k8s-titan/issues/159)). Enable Banking's own docs apply that gate only to unrestricted production ([Control Panel](https://enablebanking.com/docs/api/control-panel/)).

Czechia deserves a closer look because it is the only literal "API key" route. Credentials are an API key, client ID and secret, plus an OAuth login with George. Three things can block it. The portal's terms restrict registration to "Entrepreneurs" ([clause 3.3](https://developers.erstegroup.com/terms-and-conditions/)), while the bank's handbook names retail clients as eligible and also allows the bank to deny access, request your source code, or ask for a criminal-record extract ([handbook](https://www.csas.cz/content/dam/cz/csas/www_csas_cz/dokumenty/obecne/how-to-connect-to-api-of-cs.pdf), undated and possibly stale). Whether a loopback redirect is accepted is undocumented. And I found no report of any private person receiving production keys. An email to `api@csas.cz` should settle the first of these, and potentially the others.

Elsewhere, no George feature gives a user an API token. "ErsteConnect" sounds like one, but it is a corporate product "not designed for accessing the private accounts of retail customers" ([FAQ](https://developers.erstegroup.com/support/faq/bank.egb/c2d51860-7a34-4646-821d-a5b05fbbca6a)). Unofficial George projects exist for Austria only: two are abandoned, and two recent ones automate a logged-in browser ([mcp.directory](https://mcp.directory/skills/george), [GitHub](https://github.com/fintaro-ai/george.sparkasse.at)). A live banking session in a budgeting tool is a poor trade when an export gets the same data with no such exposure.

## The redirect and the consent clock shape the whole experience

Connecting works like this. reeve asks Enable Banking for a bank login link, you approve in your normal browser, and the bank sends your browser back to a registered address with a one-time `code`. reeve exchanges that code, signed with your key, for a session. A normal system browser matters because bank apps can fail to open from an embedded window ([FAQ](https://enablebanking.com/docs/faq/)).

**The return address is the main design problem for a local app.** The native-app standard recommends `http://127.0.0.1` ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.txt)), but Enable Banking support replied "Only https: redirect supported", and `app://` was rejected ([#7799](https://github.com/actualbudget/actual/issues/7799#issuecomment-6163485413)). Sources conflict on `https://localhost`: one tool defaults to it with paste-back ([Enablebanking-to-ofx](https://github.com/AfwasSysteem/Enablebanking-to-ofx)), and a contributor says it fails ([PR 5570](https://github.com/actualbudget/actual/pull/5570)).

This overrides the loopback callback route suggested in the reeve code review, and it rules out a `reeve://` deep link unless a hosted HTTPS page sits in front of it. **I recommend paste-back as the baseline**: the address bar ends on a harmless HTTPS page, and you paste the final URL or code into reeve ([ha-enablebanking](https://github.com/SurfHost/ha-enablebanking)). It needs no server, port or hosted page, and it works the same from the CLI, which reeve's no-server mode would otherwise struggle with. My reading is that a leaked code alone is not enough, because the exchange requires your signed JWT. This step is ugly, but it happens a few times a year per bank.

Three clocks then apply. **Consent** lapses: the law allows up to 180 days ([Reg. 2022/2360](https://lawplayer.com/eu/act/32022R2360)), and Enable Banking reports each bank's real `maximum_consent_validity`, 180 for most ([FAQ](https://enablebanking.com/docs/faq/)). Erste's Austrian and Slovak pages still say 90, and Austria's may simply be old, so read the number from the API rather than assuming it. Re-authorising issues new session and account IDs ([FAQ](https://enablebanking.com/docs/faq/)), and one user saw a Revolut reconnect duplicate every transaction in another tool ([Securo #445](https://github.com/securo-finance/securo/issues/445)). `identification_hash` reportedly stays stable ([#7799](https://github.com/actualbudget/actual/issues/7799)), so match on that.

**Fetch limits** are about four a day per account when you aren't present ([RTS Art. 36](https://lawplayer.com/eu/act/32018R0389), [Revolut](https://developer.revolut.com/docs/guides/build-banking-apps/usage-and-limits)). Headers can mark you as present, but a private IP in them causes bank errors, so Actual omits them for local clients ([PR 8032](https://github.com/actualbudget/actual/pull/8032)). Plan on four a day. That is plenty for a budget.

**Deep history** closes fast: Revolut documents 5 minutes ([Revolut](https://developer.revolut.com/docs/guides/build-banking-apps/usage-and-limits), search excerpt), and Enable Banking says generally about an hour ([FAQ](https://enablebanking.com/docs/faq/)). After that expect about 90 days, so the first fetch must run immediately after linking.

## Copy Actual's shape but not its matching

Actual supports five providers and, for new European users, only Enable Banking is live. It merged in May 2026 and is still flagged experimental ([PR 7345](https://github.com/actualbudget/actual/pull/7345), [docs](https://actualbudget.org/docs/advanced/bank-sync/enable-banking)). Its adapters are plain HTTP clients in `sync-server`, with matching in `loot-core` ([sync.ts](https://github.com/actualbudget/actual/blob/master/packages/loot-core/src/server/accounts/sync.ts)). Its Electron app can run that server on 127.0.0.1 ([index.ts](https://github.com/actualbudget/actual/blob/master/packages/desktop-electron/index.ts)), so nothing in its design requires remote hosting. reeve's single local process is a simpler fit.

Worth copying are the stateless signed JWT, the 90-day re-download window instead of "since last sync", merges that keep your edits, a persisted status per account such as `reauth-required` and `rate-limit-exceeded`, and the `/complete-auth` path that takes a code directly.

Three things are worth improving on. Actual stores no consent expiry, so a lapse only appears when a sync fails ([#9006](https://github.com/actualbudget/actual/issues/9006)); reeve should store it and warn early. Actual keeps secrets as rows in its server database with no encryption step ([secrets-service.js](https://github.com/actualbudget/actual/blob/master/packages/sync-server/src/services/secrets-service.js)). And it turns off strict ID checks for linked accounts, so a row can merge into a same-amount row with a different ID up to 7 days away. A Revolut user lost a −5.00 row, and a later comment traced that kind of loss to this match ([#9063](https://github.com/actualbudget/actual/issues/9063)). This is where reeve should knowingly depart from its reference: keep strict matching, import booked rows only at first, and start each link's history at a date the user picks. That also avoids most duplicates when moving from file imports to sync.

**The biggest job is in reeve's ledger.** `importRows` is the right core, but it covers only "the parts a file import uses". I confirmed that `imported_id` sits on the transaction (`packages/engine/src/db/schema.ts:95`) and that strict matching skips any row that already has an ID (`packages/engine/src/imports/reconcile.ts:165-168`). So a transfer between two linked accounts duplicates: the first bank's row claims the ID, and the second bank's row can't match. **A top-up from Erste to Revolut is exactly this case.** Deleted or undone rows also return on the next fetch, because deletes are hard and leave no record (the backlog stub REE-23 becomes a requirement). The sizes below are relative judgments from reading the code, not time estimates.

| Piece                                                | Size      | Note                                                                                                                                                       |
| ---------------------------------------------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Imported IDs per account, plus a dismissed-ID record | **L**     | Highest risk. A side table `(account_id, imported_id, transaction_id)` solves both problems                                                                |
| `importRows` sync behaviour and cutover              | M         | Port Actual's tests first, as 0001 requires                                                                                                                |
| Enable Banking adapter and per-bank mapping          | M         | Parse decimals directly to cents, not through float. Wrap errors so no secret reaches `StorageError.cause`                                                 |
| Connect flow and account mapping                     | M         | Smaller with paste-back                                                                                                                                    |
| Secret store                                         | M         | Start with a 0600 file under `<home>`, behind an injectable interface. Never in the book, since `export_book` copies all of it, including `undo_log`       |
| Network operation kind                               | S         | The engine has no async path today, and a fetch inside a transaction breaks other requests on the shared connection. Plan, fetch, then apply               |
| Scheduler with persisted due times                   | M         | Skippable at first: manual sync plus a warning. It must not live in the `Books` fiber                                                                      |
| Transfer detection                                   | M         | Until built, transfers between linked accounts count as spending                                                                                           |
| Web UI, fake provider, tests, e2e                    | M, M      | Patterns exist. Name things "bank" because "sync" already means the live feed                                                                              |
| Pending transactions                                 | M or none | Skip at first. Banks' pending data is weak: Erste rows reportedly carry future booking dates ([#6480](https://github.com/actualbudget/actual/issues/6480)) |

## Superseding [scope rules](../../../../docs/rules/scope.md) is narrow but touches five others

[scope rules](../../../../docs/rules/scope.md) lists "bank sync" as left out (`docs/rules/scope.md:22`), and `CLAUDE.md:5` and `:112` repeat it. Its stated reason is that bank sync is "a large surface that a local app does not need", which this report largely confirms. So superseding it should be a conscious trade of that surface for less manual entry. The new decision would be **0026**, since 0025 is taken though uncommitted.

It should bring in only read-only account information, through credentials each user holds. It should keep out payments, shared project keys, any hosted service run by the project, the sync server, CRDT sync and login to reeve itself. It should also state plainly what changes: the engine makes its first outbound calls, a third party sees bank data on its way in, and users take on a provider's terms. Budget data still goes nowhere.

| Decision   | Change         | Why                                                                                                                                                                                        |
| ---------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0001       | Supersede      | Moves read-only bank sync into scope, and records the deliberate departure from Actual's non-strict matching                                                                               |
| 0003       | Amend          | Adds operations that do network work outside a transaction, and what a book must never hold                                                                                                |
| 0006       | Amend          | Nothing can keep an operation off MCP today. Credentials need hand-declared routes and consent needs a human-only surface. This is scoping, not a security boundary                        |
| 0009       | Amend          | Keep loopback and no login, but reopen the accepted risk that a rebinding web page can read a book. Add Host and Origin checks, since a page could now burn fetch allowance or alter links |
| 0010       | Amend          | Say what a redirect-dependent flow does with no server. Paste-back mostly answers this                                                                                                     |
| 0012       | Only if needed | Only for `safeStorage` or a deep link, and I recommend neither at first                                                                                                                    |
| 0011, 0015 | None           | The lock helps, and provider rows must be picked field by field                                                                                                                            |
| 0019       | Follow         | Sync logic and status belong in the engine, not in React                                                                                                                                   |

In the same change, update `docs/architecture.md`, `docs/decisions/README.md`, the hand-written MCP instructions in `packages/mcp/src/index.ts` and `packages/cli/src/skill.ts`. The decision should also note that bank payee text becomes untrusted content visible to agents.

| 10  | Feed mapped rows to `import_transactions` with `rows` and `dryRun`, compared with the file from test 2                  | 2 hours                    | Data quality in reeve's terms, with no decision change, schema change or engine code | Too many duplicates or unusable payees                                                                      |

Test 10 is the most useful one. `import_transactions` already accepts rows (`packages/engine/src/imports/handlers.ts:47`), so a throwaway script outside reeve can show the real value of synced data before the ledger is touched.

## Conclusion

The question started as "can I plug in an API key?", and the honest answer is that the key was never the hard part. A key only proves who the app is. The bank still wants a person at intervals, a provider's free tier can be withdrawn as GoCardless's new sign-ups were, and a ledger that accepts repeated imports has to get far stricter about identity than one fed by occasional files. So treat bank sync as a convenience layered over file import, not a replacement for it.

The decision worth making is whether reducing a few clicks a month justifies a large correctness change, a new external dependency and an amended security stance, for one person with two banks. If you import monthly and tolerate the export step, improved file mapping may give most of the benefit at a fraction of the cost. If tests 4 to 10 pass and you want your budget current daily, the work is justified, and building it on a fake provider first means a change of aggregator costs one adapter rather than a rewrite.
